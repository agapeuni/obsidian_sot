**2\. 코드 레이아웃**

**들여 쓰기**

\- 들여 쓰기에 4개의 공백을 사용

\- 괄호 및 괄호 안에 같이 연결되는 라인은 수직으로 정렬

# 구분 문자와 일치 foo = long_function_name (var_one, var_two, var_three, var_four) # 4 개의 공백(추가 들여 쓰기)을 추가하여 인수와 나머지 인수를 구별 def long_function_name ( var_one, var_two, var_three, var_four) : print (var_one) # 들여 쓰기는 레벨을 추가 foo = long_function_name ( var_one, var_two, var_three, var_four)

​

# 추가 들여 쓰기가 없다. if (this_is_one_thing and that_is_another_thing) : do_something () # 구별 할 수있는 주석 추가 # 구문 강조를 지원한다. if (this_is_one_thing and that_is_another_thing) : # 주석문 do_something () # 조건부 연속 줄에 들여쓰기를 추가 if (this_is_one_thing and that_is_another_thing) : do_something ()

​

# 목록의 마지막 줄의 첫 번째 공백이 아닌 문자 아래에 정렬 my_list = [ 1, 2, 3, 4, 5, 6, ] result = some_function_that_takes_arguments ( 'a', 'b', 'c', 'd', 'e', 'f', ) # 또는 시작하는 줄의 첫 문자 아래에 줄을 정렬 my_list = [ 1, 2, 3, 4, 5, 6, ] result = some_function_that_takes_arguments ( 'a', 'b', 'c', 'd', 'e', 'f', )

**탭 또는 공백**

\- Python 3에서는 들여 쓰기를 위해 탭과 공백을 혼합하여 사용할 수 없다. 오류를 발생.

**최대 라인 길이**

\- 모든 라인을 최대 79 자로 제한

\- 더 긴 줄을 선호하기도 해서 99자까지 늘릴 수 있음.

\- 파이썬 표준 라이브러리는 보수적이며 라인을 79 자로 제한해야 한다. 

\- docstrings / comments는 72로 제한

\- 백슬래시를 사용하는 것이 적절함

with open('/path/to/some/file/you/want/to/read') as file_1, \ open('/path/to/some/file/being/written', 'w') as file_2: file_2.write(file_1.read())

**​**

**이진 연산자 전후에 줄 바꿈이 필요한가요?**

\- 권장되는 스타일은 이진 연산자 뒤로 줄바꿈을 하였지만 가독성을 떨어뜨릴 수 있다. 아래에 잘못된 예와 올바른 예를 살펴보자.

# Wrong: # operators sit far away from their operands income = (gross_wages + taxable_interest + (dividends - qualified_dividends) - ira_deduction - student_loan_interest)

# Correct: # easy to match operators with operands income = (gross_wages \+ taxable_interest \+ (dividends - qualified_dividends) \- ira_deduction \- student_loan_interest)

**​**

**빈 줄**

**-** 최상위 함수 및 클래스 정의 사이에는 두 개의 빈 줄을 사용

\- 클래스 내부의 메서드 정의는 하나의 빈 줄로 구분

\- 관련된 함수 그룹을 분리하는데 빈 줄을 사용

\- 파이썬은 control-L ( ^ L) 폼 피드 문자를 공백으로 취급한다.

​

**소스 파일 인코딩**

\- Python 배포판의 코드는 항상 UTF-8을 사용

\- ASCII (Python 2) 또는 UTF-8 (Python 3)을 사용하는 파일에는 인코딩 선언이 없어야 한다.

​

Python 3.0 이상의 경우 표준 라이브러리에 대해 다음 정책이 규정된다. ( PEP 3131 참조 ).

_" Python 표준 라이브러리의 모든 식별자는 반드시 ASCII 전용 식별자를 사용해야 하며 가능한 경우 영어 단어를 사용해야 한다. 또한 문자열 리터럴 및 주석도 ASCII 여야 한다. 단, 비 ASCII 기능을 테스트하는 사례 및 저자 이름은 예외. 라틴 알파벳 (latin-1, ISO / IEC 8859-1 문자 세트)을 기반으로 하지 않는 저자는 반드시 이 문자 세트로 이름을 음역을 사용. "_

**임포트(import)**

\- import는 별도의 행으로 구분하여 사용한다.

\- import는 항상 파일의 맨 위에, 모듈 주석 및 문서 문자열 바로 다음과 모듈 전역 및 상수 바로 앞에 배치된다.

# Correct: import os import sys

# Wrong: import sys, os

​

아래와 같이 사용하기도 한다.

# Correct: from subprocess import Popen, PIPE

**​**

*** import는 다음 순서로 그룹화해야 한다.**

1\. 표준 라이브러리 import

2\. 관련 서드파티 import

3\. 로컬 애플리케이션 / 자체 라이브러리 import

​

각 import 그룹 사이에 빈 줄을 넣는다.

**모듈 레벨 이름**

__all__ , __author__ , __version__ 등과 같은 모듈 수준 "dunders"는 모듈 docstring 뒤에 있지만 __future__ imports를 제외한 모든 import 문 앞에 배치해야 한다. 파이썬은 future import를 문서화 문자열을 제외한 다른 코드보다 먼저 모듈에 표시해야 한다.

"""This is the example module. This module does stuff. """ from __future__ import barry_as_FLUFL __all__ = ['a', 'b', 'c'] __version__ = '0.1' __author__ = 'Cardinal Biggles' import os import sys

**3\. 문자열 따옴표**

\- 파이썬에서 작은따옴표로 묶인 문자열과 큰따옴표로 묶인 문자열은 같다. 

\- 여기 PEP에서는 이에 대한 권장사항을 제시하지 않는다.

\- 그러나 문자열에 작은따옴표 나 큰따옴표가 포함된 경우 다른 문자열을 사용하여 가독성 향상을 위해 문자열에서 백 슬래시를 피함

\- 삼중 따옴표로 묶인 문자열의 경우 항상 PEP 257의 docstring 규칙과 일치하도록 큰따옴표 문자를 사용

​

**4\. 표현식과 문장의 공백**

다음과 같은 상황에서는 불필요한 공백을 피한다. 

​

중괄호, 대괄호, 괄호 안: 

# Correct: spam(ham[1], {eggs: 2}) # Wrong: spam( ham[ 1 ], { eggs: 2 } )

​

괄호, 괄호 또는 중괄호 안에 바로 :

# Correct: foo = (0,) # Wrong: bar = (0, )

​

쉼표, 세미콜론 또는 콜론 바로 앞에 : 

# Correct: if x == 4: print x, y; x, y = y, x # Wrong: if x == 4 : print x , y ; x , y = y , x

​

슬라이스에서 콜론은 이항 연산자처럼 작동하며 양쪽에 동일한 간격이 있어야 한다. 

확장 슬라이스에서 두 개의 콜론에는 동일한 간격이 적용되어야 한다.

슬라이스 매개 변수를 생략하면 공백이 생략된다. 

# Correct: ham[1:9], ham[1:9:3], ham[:9:3], ham[1::3], ham[1:9:] ham[lower:upper], ham[lower:upper:], ham[lower::step] ham[lower+offset : upper+offset] ham[: upper_fn(x) : step_fn(x)], ham[:: step_fn(x)] ham[lower + offset : upper + offset] # Wrong: ham[lower + offset:upper + offset] ham[1: 9], ham[1 :9], ham[1:9 :3] ham[lower : : upper] ham[ : upper]

​

함수 호출의 인수 목록을 시작하는 열린 괄호 바로 직전에 :

# Correct: spam(1) # Wrong: spam (1)

​

인덱싱 또는 슬라이싱을 시작하는 열린 괄호 바로 앞 :

# Correct: dct['key'] = lst[index] # Wrong: dct ['key'] = lst [index]

​

할당 연산자 주위에 공백을 배치하여 다른 연산자와 정렬

# Correct: x = 1 y = 2 long_variable = 3 # Wrong: x = 1 y = 2 long_variable = 3

**​**

**5\. 다른 권고**

**-** 어디서나 공백을 피한다. 일반적으로 보이지 않기 때문에 혼동될 수 있다. 

\- 예를 들어 하나의 공백이 있고 백슬래시와 개행은 줄 연속 표시자로 계산되지 않는다.

\- 항상 양쪽에 하나의 공백이 바이너리 연산자를 둘러싸도록 한다. 

할당 ( = ), 증강 할당 ( + = , - = 등), 비교 ( == , < , > , ! = , <> , <= , > = , in, not in, is, is not), 부울.

\- 우선순위가 다른 연산자를 사용하는 경우 우선순위가 가장 낮은 연산자 주위에 공백을 추가

\- 둘 이상의 공백을 사용하지 말고 항상 이항 연산자의 양쪽에 같은 양의 공백이 있어야 한다.

# Correct: i = i + 1 submitted += 1 x = x*2 - 1 hypot2 = x*x + y*y c = (a+b) * (a-b) # Wrong: i=i+1 submitted +=1 x = x * 2 - 1 hypot2 = x * x + y * y c = (a + b) * (a - b)

​

함수 주석은 콜론에 일반 규칙을 사용해야 하며 항상 화살표 주위에 공백이 있어야 한다.

# Correct: def munge(input: AnyStr): ... def munge() -> PosInt: ... # Wrong: def munge(input:AnyStr): ... def munge()->PosInt: ...

**​**

키워드 인수를 표시하거나 어노테이션이 없는 함수 매개 변수의 기본값을 표시할 때 = 기호 주위에 공백을 사용하지 말라.

# Correct: def complex(real, imag=0.0): return magic(r=real, i=imag) # Wrong: def complex(real, imag = 0.0): return magic(r = real, i = imag)

​

그러나 인수 어노테이션을 기본값과 결합할 때 = 기호 주위에 공백을 사용

# Correct: def munge(sep: AnyStr = None): ... def munge(input: AnyStr, sep: AnyStr = None, limit=1000): ... # Wrong: def munge(input: AnyStr=None): ... def munge(input: AnyStr, limit = 1000): ...

​

복합 문장 (같은 줄에 여러 문장)은 일반적으로 사용하지 않는 것이 좋다.

# Correct: if foo == 'blah': do_blah_thing() do_one() do_two() do_three() Rather not: # Wrong: if foo == 'blah': do_blah_thing() do_one(); do_two(); do_three()

​

짧은 줄이 있는 if / for / while을 같은 줄에 두는 것이 좋은 경우도 있지만, 다중 절에서 이 작업을 수행하지 말라.

# Wrong: if foo == 'blah': do_blah_thing() for x in lst: total += x while t < 10: t = delay()

# Wrong: if foo == 'blah': do_blah_thing() else: do_non_blah_thing() try: something() finally: cleanup() do_one(); do_two(); do_three(long, argument, list, like, this) if foo == 'blah': one(); two(); three()

​

**6\. 뒤에 오는 콤마를 사용하는 경우**

\- 일반적으로 뒤에 오는 콤마는 선택 사항이다.

\- 하나의 요소로 튜플을 만들 때 필수적이다. 

\- 명확하게 하기 위해 괄호로 둘러싸는 것이 좋다.

# Correct: FILES = ('setup.cfg',) # Wrong: FILES = 'setup.cfg',

\- 뒤에 오는 콤마가 버전 관리 시스템을 사용할 때, 값 리스트, 인수 또는 import 항목이 시간이 지남에 따라 확장될 것으로 예상되는 경우 도움이 된다.

\- 패턴은 각 값을 한 줄에 하나씩 배치하고 항상 뒤에 쉼표를 추가하고 다음 줄에 닫는 괄호를 추가한다.

\- 닫는 구분 기호와 동일한 줄에 뒤에 오는 콤마를 사용하는 것은 의미가 없다.

# Correct: FILES = [ 'setup.cfg', 'tox.ini', ] initialize(FILES, error=True, ) # Wrong: FILES = ['setup.cfg', 'tox.ini',] initialize(FILES, error=True,)

​

**7\. 주석(Comment)**

\- 코드와 모순되는 주석은 주석이 없는 것보다 나쁘다

\- 코드가 변경될 때 항상 주석을 최신 상태로 유지한다.

\- 주석은 완전한 문장이어야 하고 첫 단어는 소문자로 시작하는 식별자가 아닌 한 대문자로 표기해야 한다.

\- 블록 주석은 일반적으로 완전한 문장으로 구성된 하나 이상의 단락으로 구성되며 각 문장은 마침표로 끝난다.

\- 마지막 문장 이후를 제외하고 문장 끝에는 문장 주석에서 두 칸을 사용해야 한다.

\- 의견을 명확하고 이해하기 쉬운 다른 언어 사용자가 이해할 수 있도록 한다.

​

**블록 주석(Block comments)**

\- 블록 주석은 일반적으로 그 뒤에 오는 일부 코드에 적용되며 해당 코드와 동일한 수준으로 들여 쓰기 된다.

\- 블록 주석의 각 줄은 '#' 과 단일 공백으로 시작한다. (주석 안에 텍스트가 들여 쓰기 되지 않은 경우)

\- 블록 주석 내의 단락은 단일 '#'을 포함하는 행으로 구분된다.

**​**

**인라인 주석**

\- 인라인 주석은 간간이 사용한다.

\- 인라인 주석은 명령문과 같은 행에 대한 주석이다.

\- 인라인 주석은 명령문에서 최소한 두 공백으로 분리해야 한다. 

\- '#'과 단일 공백으로 시작해야 한다.

\- 인라인 주석은 불필요하며 명확하지 않으면 산만하다.

x = x + 1 # Increment x x = x + 1 # Compensate for border

​

**문서화 문자열(docstring)**

**-** 좋은 문서화 문자열(docstrings)을 작성하기 위한 규칙은 PEP 257을 참고한다.

\- 모든 public 모듈, 함수, 클래스 및 메서드에 대한 docstring을 작성한다.

\- Non-public 메서드에는 문서화 문자열이 필요하지 않지만 메서드의 기능을 설명하는 주석이 있어야 하고 이 주석은 def 줄 다음에 나타난다.

\- PEP 257 은 훌륭한 문서 문자열 규칙을 설명한다.

\- 가장 중요한 것은 여러 줄의 docstring을 끝내는 "" "는 한 줄에 있어야 한다.

"""Return a foobang Optional plotz says to frobnicate the bizbaz first. """

**​**

**8\. 명명 규칙**

\- 파이썬 라이브러리의 명명 규칙은 약간 엉망이므로, 완전한 일관성을 유지하기 힘들다. 

\- 그럼에도 불구하고 현재 권장되는 명명 표준이 있다. 

\- 새로운 모듈 및 패키지는 이러한 표준에 작성해야 하지만 기존 라이브러리의 스타일이 다른 경우 내부 일관성이 선호된다.

**공용 및 내부 인터페이스**

이전 버전과의 호환성 보증은 공용 인터페이스에만 적용된다. 따라서 사용자는 공용 인터페이스와 내부 인터페이스를 명확하게 구분할 수 있어야 한다. 

​

문서화된 인터페이스가 일반적인 하위 호환성 보장에서 제외되는 임시 또는 내부 인터페이스라고 명시 적으로 선언하지 않는 한 문서화된 인터페이스는 공용으로 간주된다. 문서화되지 않은 모든 인터페이스는 내부 인터페이스로 가정해야 한다.

​

내부 검사를 보다 잘 지원하려면 모듈이 __all__ 속성을 사용하여 공개 API에서 이름을 명시 적으로 선언해야 한다. __all__ 을 빈 목록으로 설정하면 모듈에 공개 API가 없음을 나타낸다.

​

__all__을 적절하게 설정하더라도 내부 인터페이스 (패키지, 모듈, 클래스, 함수, 특성 또는 기타 이름) 앞에는 단일 밑줄이 붙어야 한다.

​

포함하는 네임 스페이스 (패키지, 모듈 또는 클래스)가 내부로 간주되면 인터페이스도 내부로 간주된다.

​

가져온 이름은 항상 구현 세부 사항으로 간주되어야 한다. 다른 모듈은 포함된 모듈의 API에서 명시 적으로 문서화된 부분 (예 : os.path 또는 하위 모듈에서 기능을 노출하는 패키지의 __init__ 모듈)이 아닌 한 가져온 이름에 대한 간접 액세스에 의존해서는 안 된다.

**9\. 프로그래밍 추천**

\- 코드는 다른 Python 구현 (PyPy, Jython, IronPython, Cython, Psyco 등)에 불리하지 않은 방식으로 작성해야 한다.

\- None과 같이 개체에 대한 비교는 평등 연산자가 아니라 is 또는 is not과 함께 해야 한다.

​

Not ... is 연산자보다는 is not 연산자를 사용. 두 표현 모두 기능적으로 동일하지만 전자가 더 읽기 쉽고 선호된다.

# Correct: if foo is not None: # Wrong: if not foo is None:

# Correct: def f(x): return 2*x # Wrong: f = lambda x: 2*x

​

람다 식을 식별자에 직접 바인딩 하는 할당문 대신 항상 def 문을 사용한다.

BaseException 대신 Exception에서 예외를 파생 시킨다.

BaseException에서 직접 상속은 예외를 잡는 것이 거의 항상 잘못된 경우를 위해 예약되어 있다.

​

예외 체인을 적절하게 사용한다. 

파이썬 3에서 "raise X from Y"는 원래 역 추적을 잃지 않으면 서 명시적인 대체를 나타 내기 위해 사용해야 한다.

​

예외를 잡을 때 except: 절을 사용하는 대신 가능할 때마다 특정 예외를 언급한다.

try: import platform_specific_module except ImportError: platform_specific_module = None

​

발견된 예외를 이름에 바인딩 할 때 Python 2.6에 추가된 명시적인 이름 바인딩 구문을 선호한다.

try: process_data() except Exception as exc: raise DataProcessingFailedError(str(exc))

​

모든 try / except 절에 대해 try 절을 필요한 최소 코드 양으로 제한한다.

# Correct: try: value = collection[key] except KeyError: return key_not_found(key) else: return handle_value(value) # Wrong: try: # Too broad! return handle_value(collection[key]) except KeyError: # Will also catch KeyError raised by handle_value() return key_not_found(key)

​

컨텍스트 관리자는 자원을 확보 및 해제하는 것 이외의 작업을 수행할 때마다 별도의 함수 또는 메서드를 통해 호출해야 한다.

# Correct: with conn.begin_transaction(): do_stuff_in_transaction(conn) # Wrong: with conn: do_stuff_in_transaction(conn)

​

return 구문에서 일관성을 유지. 함수의 모든 return 문은 식을 반환하거나 그중 어느 것도 반환하지 않아야 한다.

return 문이 표현식을 리턴하는 경우, 값이 리턴되지 않은 리턴 문은 이를 명시 적으로 return None으로 명시해야 하며 함수 끝에 도달할 수 있는 경우 명시적 return 문이 있어야 한다.

# Correct: def foo(x): if x >= 0: return math.sqrt(x) else: return None def bar(x): if x < 0: return None return math.sqrt(x) # Wrong: def foo(x): if x >= 0: return math.sqrt(x) def bar(x): if x < 0: return return math.sqrt(x)

**함수 주석**

\- PEP 484를 수용함에 따라 기능 주석에 대한 스타일 규칙이 변경되고 있다.

\- 순방향 호환을 위해 Python 3 코드의 함수 주석은 PEP 484 구문을 사용해야 한다. 

\- 이 PEP에서 이전에 권장된 주석 스타일 실험은 더 이상 권장되지 않는다.

\- 그러나 stdlib 외부에서는 PEP 484 규칙 내 실험 이 권장된다. 

\- 예를 들어, PEP 484 스타일의 주석을 사용하여 큰 타사 라이브러리 또는 응용 프로그램을 마크 업하고, 주석을 추가하는 것이 얼마나 쉬운지 검토하고 해당 주석의 존재 여부가 코드 이해성을 높이는지를 관찰한다.

\- 파이썬 표준 라이브러리는 그러한 주석을 채택하는 데 보수적이어야 하지만 새로운 코드와 대형 리팩토링에 사용할 수 있다.

​

함수 주석을 다르게 사용하려는 코드의 경우 다음 형식의 주석을 추가하는 것이 좋다.

**변수 주석**

\- 스타일 권장 사항은 위에서 설명한 함수 주석에 대한 권장 사항과 비슷하다.

\- 모듈 수준 변수, 클래스 및 인스턴스 변수 및 로컬 변수에 대한 주석은 콜론 뒤에 단일 공백이 있어야 한다.

\- 콜론 앞에 공백이 없어야 한다.

\- 배정에 오른쪽이 있으면 등호 부호의 양쪽에 정확히 하나의 공백이 있어야 한다.

# Correct: code: int class Point: coords: Tuple[int, int] label: str = '<unknown>' # Wrong: code:int # No space after colon code : int # Space before colon class Test: result: int=0 # No spaces around equality sign
