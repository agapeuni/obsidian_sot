# 2023-07-24 223164967653 리팩토링 - 클린 코드의 첫걸음, 나쁜 냄새부터 잡아라

## 본문

![](https://postfiles.pstatic.net/MjAyNTA0MTZfMjcg/MDAxNzQ0ODE0OTk3MDc0.rVoIpzfUsbFXSW_h3wwfn8n-aW-Kth42BOvPWkV-z5cg.ui_HxCFEQUHJk0kWsKlOrl7LqV6AQbb7rv2H6YrRGt0g.PNG/Java-001_\(10\).png?type=w80_blur)

​

소프트웨어 개발 과정에서 '코드의 나쁜 냄새(Code Smell)'란 코드의 구조나 디자인 측면에서 드러나는 문제적 패턴 혹은 스타일의 이상 징후를 의미한다. 이러한 냄새는 코드의 가독성, 유지보수성, 확장성을 저해하며, 잠재적으로 버그를 유발할 가능성이 있다. 

​

좋은 개발자는 자신이 작성한 코드뿐만 아니라 타인이 작성한 코드에서도 이러한 ‘냄새’를 인지하고, 리팩토링(refactoring)을 통해 문제를 개선하는 역량을 갖추고자 노력한다. 자신이 직업 작성한 코드나 다른 사람이 작성한 소스 코드를 리뷰하며 경험을 통해 나쁜 냄새를 찾을 수 있는 능력을 키우고, 지속적인 개선을 통해 좋은 코드를 만들어 나가는 것이 중요하다.

​

리팩토링은 기존 코드의 기능을 변경하지 않으면서, 구조나 설계를 개선하는 작업을 의미한다. 아래는 개발자들이 자주 마주치는 코드의 나쁜 냄새 유형과 그에 따른 리팩토링 기법을 정리한 내용이다. 코드 리팩토링을 할 때는 기존 기능을 변경하지 않으면서 코드의 구조나 디자인을 개선한다. 

​

본 포스트에서는 리팩토링이 필요한 항목을 정리해 본다. 

**1\. 중복된 코드**

같은 코드가 여러 곳에 반복적으로 등장할 때.

​

  * Extract Method

  * Pull Up Method

  * Form Template Method

  * Substitute Algorithm

  * Extract Class 

​

​

**2\. 긴 메서드**

한 메서드가 너무 많은 일을 처리하고 있을 때.

​

  * Extract Method

  * Replace Temp with Query

  * Introduce Parameter Object

  * Preserve Whole Object

  * Replace Method with Method Object

  * Decompose Conditional 

​

**3\. 거대한 클래스**

하나의 클래스가 과도하게 많은 책임을 지고 있을 때.

사실 거대하다, 길다 이런 표현의 정확성이 의문이 가지만 기준을 세운다는 것도 모호한 점이 있다.

​

  * Extract Class

  * Extract Subclass

  * Duplicate Observed Data

**4\. 긴 파라미터 리스트**

메서드 호출 시 전달해야 할 매개변수가 너무 많을 때.

​

  * Replace Parameter with Method

  * Preserve Whole Object

  * Introduce Parameter Object 

​

**5\. 확산적 변경(Divergent Change)**

하나의 클래스가 다양한 이유로 자주 변경될 때.

클래스 하나만을 기준으로 하여 내/외부의 변동으로 클래스 내부의 여러 지점에 변동이 일어날 때.

​

  * Extract Class

**6\. 산탄총 수술(Shotgun Surgery)**

하나의 변경이 여러 클래스에 영향을 미쳐 많은 부분을 동시에 수정해야 할 때.

공통적으로 변동되는 것들을 한 데 묶거나 따로 떼어내는 게 관건인 듯.

​

  * Move Method

  * Move Field

  * Inline Class

**7\. 기능에 대한 욕심(Feature Envy)**

한 클래스가 다른 클래스의 데이터에 과도하게 의존할 때 

한 클래스 내부에서 다른 클래스 내부의 데이터나 멤버를 빈번하게 호출하거나 사용한다는 것은 그 클래스로의 이동을 생각해 봐야 한다. 예외 : GOF의 Strategy, Visitor, Kent Beck의 Self Delegation 패턴들

​

  * Move Method

  * Extract Method

​

**8\. 데이터 덩어리(Data Clump)**

항상 함께 사용되는 데이터 묶음이 존재할 때 

​

  * Extract Class

  * Introduce Parameter Object

  * Preserve Whole Object

**​**

**9\. 기본 타입에 대한 강박관념(Primitive Obsession)**

객체 대신 기본 타입을 과도하게 사용할 때 

항상 몰려다니는 데이터들에 대해 클래스로 묶는 것에 두려워 말라!

​

  * Replace Data Value with Object

  * Replace Type Code with Class

  * Replace Type Code with State/Strategy

  * Extract Class

  * Introduce Parameter Object

  * Replace Array with Object

**10\. Switch 문**

다형성을 생각하라.

조건 분기문이 많고 복잡하여 다형성(polymorphism)으로 대체 가능한 경우 

​

  * Extract Method

  * Move Method

  * Replace Type Code with Subclasses

  * Replace Type Code with State/Strategy

  * Replace Conditional with Polymorphism

  * Replace Parameter with Explicit Methods

  * Introduce Null Object

**11\. 평생 상속 구조(Parallel Inheritance Hierarchies)**

하나의 클래스에 서브클래스를 만들면 다른 클래스에도 동일하게 서브클래스를 생성해야 하는 구조 

한 단위의 상속 구조의 클래스 접두어가 다른 상속 단위의 클래스들의 접두어와 같다면?

​

  * Move Method

  * Move Field

**12\. 게으른 클래스 (Lazy Class)**

역할이 거의 없는 클래스 

하는 일이 거의 없는 클래스에게 최후를!

​

Collapse Hierarchy

  * Inline Class

**13\. 추측성 일반화(Speculative Generality)**

아직 필요하지 않은 기능을 위해 지나치게 일반화된 코드가 있을 때 

어떤 기능이 필요한 경우가 일반적이라서 미리 그러한 처리를 위한 대비책을 다 만들어 두는 경우.

​

  * Collapse Hierarchy

  * Inline Class

  * Remove Parameter

  * Rename Method

**14\. 임시 필드 (Temporary Field)**

특정 상황에서만 값이 할당되고 사용되는 인스턴스 또는 변수들.

이 변수를 사용하는 코드를 새로운 클래스에 모은다.

​

  * Extract Class

  * Introduce Null Object

**15\. 메시지 체인(Message Chains)**

한 객체가 또 다른 객체에 접근하고, 그 객체가 또 다른 객체에 접근하는 방식 

객체를 얻기 위해 다른 객체에게 묻고, 그 객체는 또 다른 객체에 묻고, blur blur...

getMoive().getPriceCode().getPrice()...

​

  * Hide Delegate

  * Extract Method

  * Move Method

**16\. 미들 맨(Middle Man)**

중간 클래스가 위임만 수행하고 실질적인 로직은 없을 때 

캡슐화로 인해 내부를 알 필요는 없는데 메서드 대부분이 다른 클래스의 의존적이다? 

위임 Delegation이 많이 일어났다. 이 위임된 객체들이 미들 맨에 해당.

​

  * Remove Middle Man

  * Inline Method

  * Replace Delegation with Inheritance

​

**17\. 부적절****Method**

클래스 간의 의존 관계나 메서드 위치가 부적절할 때 

​

  * Move Field

  * Change Bidirectional Association to Unidirectional

  * Extract Class

  * Hide Delegate

  * Replace Inheritance

​

**18\. 다른 인터페이스를 가진 대체 클래스**

동일한 기능을 수행하지만 시그니처가 다른 클래스가 있을 때 

​

  * Rename Method

  * Move Method

  * Extract Superclass

**19\. 불완전한 라이브러리 클래스**

외부 라이브러리에서 기능 확장이 필요하지만 수정이 불가능할 때 

​

  * Introduce Foreign Method

  * Introduce Local Extension

**20\. Data Class**

데이터를 담고 있는 것 외에는 기능이 없는 클래스. 

멍청하게 데이터만 저장하고 다른 클래스에 의해서 조작만 되는 꼭두각시 클래스.

​

  * Encapsulate Field

  * Encapsulate Collection

  * Remove setting Method

  * Move Method

  * Extract Method

  * Hide Method

**21\. 거부된 유산(Refused Bequest)**

서브클래스가 슈퍼클래스의 인터페이스를 원하지 않음에도 상속을 받는 경우.

서브 클래스가 동작은 재사용하지만 슈퍼클래스의 인터페이스를 지원하는 것은 원치 않는다?

​

  * Push Down Method

  * Push Down Field

  * Replace Inheritance with Delegation

**22\. 주석**

주석 없이도 코드를 이해할 수 있도록 리팩토링하는 것이 바람직 

주석을 써야 할 것 같은 생각이 들면, 먼저 코드를 리팩토링하여 주석이 불필요하도록 하라.

  * Extract Method 

  * Rename Method 

  * Introduce Assertion
