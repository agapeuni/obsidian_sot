관계형 데이터 베이스 언어 표준

ANSI SQL은 미국 국가 표준 협회(ANSI)에서 제정한 SQL(Structured Query Language)의 표준화를 위한 표준이다. ANSI SQL은 데이터베이스 시스템 간에 호환성과 이식성을 보장하기 위해 정의되었다. 관계형 데이터베이스 언어 표준에는 다양한 버전이 있다.

​

1) ANSI SQL/86

1986년에 처음으로 발표된 ANSI SQL 표준이다. 이 버전은 초기 관계형 데이터베이스 시스템에서 사용된 SQL 문법의 기본적인 요소를 정의한다.

​

2) ANSI SQL/89

이 버전은 1989년에 발표되었다. ANSI SQL/86과 거의 동일한 기능을 제공하지만 몇 가지 문법적인 개선이 이루어졌다. 주요한 변경 사항은 표준 JOIN 구문의 추가, NULL 값 처리 방법의 명확한 정의 등이 있다.

​

3) ANSI SQL/92

이 버전은 1992년에 발표된 ANSI SQL 표준의 중요한 업데이트다. ANSI SQL/92는 현재까지 가장 널리 사용되는 SQL 표준이다. 이 버전에서는 데이터 정의, 데이터 조작, 데이터 제어 등 다양한 측면에서 SQL의 확장된 기능이 추가되었다. 또한, OUTER JOIN, VIEW, 트랜잭션 제어, 서브쿼리 등과 같은 기능이 도입되었다.

​

4) ANSI SQL:1999

1999년에 발표된 표준으로, 객체 관계형 기능과 XML 처리 기능이 주요 변경 사항이다. 객체 관계형 기능은 상속, 다형성, 사용자 정의 데이터 유형 등을 포함한다. 또한, XML 데이터를 처리하기 위한 새로운 데이터 유형과 연산자가 도입되었다.

​

5) ANSI SQL:2003

2003년에 발표된 표준으로, XML 처리 기능과 함께 윈도우 함수, 집계 확장 기능 등이 추가되었다. 윈도우 함수는 행 그룹에 대해 계산을 수행하고 결과를 반환하는 함수로, 분석적인 쿼리를 작성할 때 유용하다.

​

6) ANSI SQL:2008

2008년에 발표된 표준으로, 트리거, 일반화 집합, 범위 변수 등이 도입되었다. 트리거는 데이터베이스의 특정 이벤트(INSERT, UPDATE, DELETE 등)가 발생했을 때 자동으로 실행되는 프로그램이다. 일반화 집합은 데이터베이스 내에서 다양한 집합 연산을 수행할 수 있는 기능이다. 범위 변수는 트리거와 저장 프러시저에서 사용할 수 있는 변수다.

​

7) ANSI SQL:2011

2011년에 발표된 표준으로, 분석 함수, XML 관련 기능 등이 추가되었다. 분석 함수는 행 집합에 대해 통계적 분석을 수행하고 결과를 반환하는 함수로, 데이터의 패턴이나 동향을 파악하는 데 사용된다. 또한, XML 관련 기능은 XML 데이터를 저장, 검색, 조작하는 데 필요한 연산과 기능을 정의한다.

1장 데이터 모델 설계

방법 1 모든 테이블에 기본키가 있는지 확인하자

모든 테이블에는 컬럼 한 개 이상으로 구성된 기본키(Primary Key)가 있어야 한다. 관계형 데이터베이스에서 참조 무결성 개념은 매우 중요하다. 기본키로 숫자가 좋은지 텍스트가 좋은지는 데이터베이스 전문가 사이에서도 의견이 갈린다.

방법 2 중복으로 저장된 데이터 항목을 제거하자

중복 데이터를 저장하면서 일으키는 문제점을 정규화를 통해 해결할 수 있다. 정규화의 목표는 반복되는 데이터를 최소화하는 것이다.

​

​

방법 3 반복 그룹을 제거하자

반복 그룹은 속성별로 묶은 보고서를 쿼리로 생성하기 어렵다. 비용 측면에서 컬럼은 비싸고 로우는 저렴하다.

![](https://postfiles.pstatic.net/MjAyMzA2MjRfODAg/MDAxNjg3NTQzMjA3NzY1.XzG4LFk7SaLvQLdLsC54c-N_1AoZhhDv9VA-dCDzV6Ug.qICAeb4S252h6MkuKTi1VM9qwo1T5FrTllNpy1cuz8Yg.PNG.agapeuni/img1.daumcdn.png?type=w80_blur)

UNION 쿼리에서 ORDER BY 절은 마지막 SELECT에서 사용할 수 있다.

SELECT ID AS DrawingID, Predecessor_1 AS Predecessor FROM Assignments WHERE Predecessor_1 IS NOT NULL UNION SELECT ID AS DrawingID, Predecessor_2 AS Predecessor FROM Assignments WHERE Predecessor_2 IS NOT NULL UNION SELECT ID AS DrawingID, Predecessor_3 AS Predecessor FROM Assignments WHERE Predecessor_3 IS NOT NULL UNION SELECT ID AS DrawingID, Predecessor_4 AS Predecessor FROM Assignments WHERE Predecessor_4 IS NOT NULL UNION SELECT ID AS DrawingID, Predecessor_5 AS Predecessor FROM Assignments WHERE Predecessor_5 IS NOT NULL ORDER BY DrawingID, Predecessor;

​

방법 4 컬럼당 하나의 특성만 저장하자

관계 테이블은 오직 하나의 주제에 대해서 기술한다. 컬럼은 관계로 정의된 주제를 기술하는 데이터를 포함한다. 단일 컬럼에 두 개 이상의 데이터를 저장하는 것은 좋은 생각이 아니다. 검색이나 그루핑을 어렵게 한다.

​

​

방법 5 왜 계산 데이터를 저장하면 좋지 않은지 이해하자

트리거는 작성하기 어렵고 비용도 많이 든다. 결과가 필요할 때마다 집계해 계산하는 서브 쿼리로 조인하는 것이 훨씬 효율적이다. 오라클에서 계산 컬럼을 만들려면 GENERATED ALWAYS AS 구문을 이용한다.

​

​

방법 6 참조 무결성을 보호하려면 외래키를 정의하자

데이터베이스 스키마를 제대로 설계하려면 관련된 부모 테이블의 기본키 값을 포함하도록 테이블에 외래키를 정의하는 것이 좋다. 선언적으로 참조 무결성을 정의하면 테이블 간의 관계를 알 수 있다.

​

​

방법 7 테이블 간 관계를 명확히 하자

컬럼의 데이터 타입이 같으면 테이블 간 관계를 맺을 수 있다. 상황에 따라 XML이나 JSON을 저장할 수 있는 속성 컬럼을 생성하는 것도 좋다.

​

​

방법 8 제3정규화로도 부족하다면 더 정규화하자

대부분의 애플리케이션은 제3정규화로 충분하다. 비즈니스 규칙 때문에 데이터 모델은 높은 정규화 형식을 이미 만족하고 있다.

​

​

방법 9 데이터 웨어하우스에는 역정규화를 사용하자

조인이 많을수록 옵티마이저가 최적의 실행 계획을 찾기가 어려워 읽기 성능은 떨어질 수 있다. 역정규화된 데이터베이스는 읽기 작업이 많을 때 효과적이다.

​

​

2장 인덱스 설계와 프로그램적 처리

데이터 모델을 잘 설계했다고 해서 효율적인 SQL을 작성할 수 있는 것은 아니다. 테이블에 적절한 인덱스를 만들어야 SQL 쿼리가 잘 수행이 된다.

​

방법 10 인덱스를 만들 때는 널을 고려하자

관계형 데이터베이스에서 널은 데이터가 들어 있지 않음을 나타내는 특별한 값이다. MySQL은 널 값이 있는 컬럼에 유일 인덱스를 만들 수 있다. IS NULL과 IS NOT NULL 조건을 검사할 때 인덱스가 있으면 사용한다. Oracle은 인덱스에 널 값을 허용하지 않으며 기본키에도 널 값을 넣을 수 없다.

​

​

방법 11 인덱스와 데이터 스캔을 최소화하도록 인덱스는 신중히 만들자

데이터베이스 엔진이 적합한 레코드를 찾으려고 인덱스와 데이터 페이지를 스캔하는 것을 각각 인덱스 스캔, 테이블 스캔이라고 한다. 인덱스를 만들 때는 컬럼의 조합도 중요하다. 쿼리를 튜닝하면 적은 비용으로 효과를 볼 수 있다. 많은 인덱스는 데이터의 갱신 속도를 느리게 하고 데이터 검색도 빠르지 않다.

​

​

방법 12 인덱스를 단순 필터링 이상의 목적으로 사용하자

적절하게 인덱스를 잘 만들게 되면 조인하는 시간을 단축시킨다. 중첩 루프(Nested Loop) 조인은 기본적인 조인 알고리즘이다. 해시(Hash) 조인은 조인에 참여하는 한쪽 테이블 데이터를 해시 테이블로 만든 후 다른 쪽 테이블의 각 로우를 빠르게 탐색한다. 소트머지(Sort-Merge) 조인은 조건에 따라 두 테이블을 정렬한 후에 지퍼처럼 정렬된 두 항목을 결합하는 식으로 수행된다.

​

​

방법 13 트리거를 남발하지 말자

일반적으로 트리거는 이식성이 좋지 않다. 제약 조건을 사용하면 데이터베이스 엔진이 자동으로 데이터베이스의 무결성을 강화한다.

​

​

방법 14 데이터의 부분 집합을 포함하거나 제외하려면 필터링된 인덱스를 사용하자

필터링된 인덱스나 부분 인덱스는 비클러스터드 인덱스이며, 테이블에 있는 일부 로우 집합만 포함한다. 필터링된 인덱스를 사용하면 전통적인 인덱스에 비해 성능이 월등히 좋아진다.

​

​

방법 15 프로그래밍으로 검사하는 대신 선언적 제약 조건을 사용하자

데이터베이스에서 데이터 무결성 강화는 아주 중요하다. SQL은 테이블 규칙을 명시하는 방식으로 제약 조건을 제공한다.

​

**여섯 가지 제약 조건**

  1. NOT NULL

  2. UNIQUE

  3. PRIMARY KEY

  4. FOREION KEY

  5. CHECK

  6. DEFAULT

​

​

방법 16 자신이 사용하고 작성하는 SQL의 종류를 파악하자

효율적으로 SQL 문을 작성하려면 사용 중인 DBMS가 어떤 종류인지는 Oracle은 Boolean 타입을 지원하지 않는다.

​

​

방법 17 인덱스에서 계산 결과를 사용할 시기를 파악하자

인덱스를 과다하게 만들면 UPDATE 작업이 느리게 된다.
