# LLM 애플리케이션 아키텍처

## 기준 구조

```text
사용자·업무 시스템
  → 인증·권한
  → 입력 검증·정책
  → 오케스트레이션
      ├─ 프롬프트·컨텍스트 구성
      ├─ RAG 검색·재랭킹
      ├─ 모델 호출
      └─ 도구·MCP 호출
  → 출력 검증·인용
  → 응답·후속 작업
  → 로그·추적·평가
```

## 계층별 책임

| 계층 | 책임 | 핵심 위험 |
|---|---|---|
| 채널 | 웹, 메신저, API 입력 | 사용자 오인, 입력 누락 |
| 인증·권한 | 사용자와 데이터 접근 통제 | 권한 상승, 정보 유출 |
| 오케스트레이션 | 상태, 분기, 재시도, 모델·도구 선택 | 무한 반복, 중복 실행 |
| 지식 | 문서 수집, 검색, 인용 | 오래된 정보, 권한 무시 |
| 모델 | 생성, 분류, 추출, 추론 | 환각, 편향, 불안정성 |
| 도구 | 외부 시스템 읽기·쓰기 | 파괴적 실행, 비용 발생 |
| 관측 | 로그, 추적, 지표, 평가 | 민감정보 로그 노출 |

## 설계 원칙

1. 모델은 시스템 전체가 아니라 불확실한 판단을 담당하는 구성요소다.
2. 결정 가능한 규칙은 코드로, 의미 판단은 모델로 분리한다.
3. 읽기와 쓰기 권한을 분리하고 외부 변경에는 승인 단계를 둔다.
4. 모든 답변보다 추적 가능한 입력·모델·프롬프트·근거·출력을 남긴다.
5. 실패 시 안전한 기본값과 수동 처리 경로를 제공한다.

## 설계 결정 기록

| 결정 | 최소 기록 항목 |
|---|---|
| 모델 선택 | 후보, 평가셋, 품질, 비용, 지연시간, 데이터 경계 |
| RAG 적용 | 원본 신뢰도, 분할, 검색, 권한, 인용, 갱신 주기 |
| Agent 적용 | 목표, 도구, 승인 경계, 종료 조건, 롤백 |
| 외부 도구 연동 | 인증 주체, 최소 권한, 멱등성, 감사 로그 |
| 운영 배포 | SLO, 평가 게이트, 알림, 장애 대응, 폐기 기준 |

## 실패 패턴

- 모델 호출 성공을 업무 처리 성공으로 오인한다.
- 검색·도구·모델 로그의 상관관계 ID가 없어 장애를 재현하지 못한다.
- 사용자 권한이 검색과 도구 호출 단계에서 유실된다.
- 프롬프트·모델·색인 버전이 따로 변경되어 회귀 원인을 찾지 못한다.
