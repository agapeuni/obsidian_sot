# Microsoft Power Automate 실무 자동화

## 현업 프로세스를 안전하고 운영 가능한 흐름으로 바꾸는 법

> [!info] 원고 상태
> 이 문서는 책의 **1차 초안**이다. 제품 화면과 라이선스는 변경될 수 있으므로 출간 전 Microsoft 공식 문서를 기준으로 재검증한다. 기능 확인 기준일은 **2026-08-15**다.

## 책의 한 문장

Power Automate의 버튼 사용법이 아니라, 반복 업무를 발견하고 설계하며 장애와 보안까지 책임지는 **운영 가능한 자동화 시스템**을 만드는 법을 설명한다.

## 예상 독자

- 이메일, 승인, 보고, 파일 정리 같은 반복 업무를 줄이고 싶은 실무자
- 팀 단위 자동화 도입을 추진하는 PM과 관리자
- Microsoft 365, SharePoint, Teams를 업무 기반으로 사용하는 조직
- 클라우드 흐름과 데스크톱 RPA를 함께 설계하려는 개발자
- 개인 자동화를 조직의 표준 자산으로 확장하려는 Power Platform 담당자

## 이 책을 읽고 할 수 있는 일

1. 자동화 후보를 비용·효과·위험 기준으로 선별한다.
2. 자동·즉시·예약 클라우드 흐름과 데스크톱 흐름을 구분해 설계한다.
3. Outlook, Teams, Forms, SharePoint, Excel, Approvals를 연결한다.
4. 조건, 반복, 변수, 식, 오류 처리로 견고한 흐름을 만든다.
5. 솔루션, 환경 변수, 연결 참조로 개발·테스트·운영 환경을 분리한다.
6. DLP 정책, 권한, 서비스 계정, 감사 로그를 포함한 거버넌스를 설계한다.
7. 실패율, 처리 시간, 절감 시간, 재처리 건수를 측정해 자동화의 가치를 증명한다.

# 머리말

업무 자동화 프로젝트가 실패하는 가장 흔한 이유는 도구가 부족해서가 아니다. 자동화할 업무를 충분히 이해하지 않은 채 화면부터 만들기 때문이다. “메일이 오면 파일을 저장한다”는 문장은 단순해 보이지만, 실제 운영에서는 질문이 이어진다.

- 어떤 발신자와 제목을 신뢰할 것인가?
- 동일한 파일이 다시 오면 덮어쓸 것인가?
- 파일명이 잘못되었거나 암호화되어 있으면 어떻게 할 것인가?
- 담당자가 퇴사해 연결 계정이 사라지면 누가 복구할 것인가?
- 실패 사실을 누가, 언제, 어떤 정보와 함께 받을 것인가?

자동화는 단순히 사람의 클릭을 없애는 일이 아니다. 업무 규칙을 명시하고, 입력과 예외를 통제하며, 결과를 추적할 수 있게 만드는 일이다. 작은 흐름 하나도 운영 시스템이라는 관점에서 다뤄야 한다.

Microsoft Power Automate는 클라우드 서비스 간 워크플로, PC 화면을 조작하는 데스크톱 RPA, 승인, 프로세스 분석, AI 기능을 하나의 생태계에서 제공한다. Microsoft의 현재 공식 설명에 따르면 주요 흐름은 자동·즉시·예약 트리거를 사용하는 클라우드 흐름과 웹·데스크톱 작업을 자동화하는 데스크톱 흐름으로 구분된다. 일부 생성형 기능은 미리 보기 상태일 수 있으므로 운영 적용 전 지원 범위와 정책을 확인해야 한다.

이 책은 기능 목록을 순서대로 나열하지 않는다. 실제 프로젝트의 흐름을 따라간다.

```text
업무 발견 → 후보 평가 → 프로세스 설계 → 흐름 구현
→ 예외 처리 → 테스트 → 배포 → 모니터링 → 개선
```

각 장의 실습은 “정상 동작”만 확인하지 않는다. 실패 조건과 로그 위치, 복구 방법, 완료 기준까지 함께 다룬다. 자동화는 실행되었다는 사실보다 **예측 가능하게 운영되는가**가 더 중요하기 때문이다.

# 1장. Power Automate를 업무 시스템으로 이해하기

## 1.1 Power Automate란 무엇인가

Power Automate는 애플리케이션과 서비스 사이의 작업을 연결하는 워크플로 자동화 서비스다. 파일 동기화, 알림, 데이터 수집처럼 반복되는 작업에서 시작해 조직의 승인, 데이터 처리, 레거시 시스템 RPA까지 확장할 수 있다.

Power Platform 안에서 각 제품은 서로 다른 역할을 맡는다.

| 제품 | 핵심 역할 | Power Automate와의 관계 |
|---|---|---|
| Power Apps | 업무용 앱 구성 | 앱의 버튼과 데이터 변경으로 흐름 실행 |
| Power BI | 데이터 분석과 시각화 | 새 데이터 처리나 알림 자동화 |
| Power Pages | 외부 사용자용 사이트 | 제출 데이터 후속 처리 |
| Copilot Studio | 대화형 에이전트 | 에이전트가 업무 흐름 호출 |
| Dataverse | 비즈니스 데이터 저장 | 트랜잭션과 권한을 포함한 자동화 기반 |

Power Automate의 장점은 코드를 전혀 쓰지 않는다는 데 있지 않다. 업무 담당자와 개발자가 같은 흐름을 보며 규칙을 논의할 수 있다는 데 있다. 시각적 설계는 협업의 문턱을 낮추지만 복잡성이 사라지는 것은 아니다. 데이터 구조, 인증, 예외 처리, 배포와 운영은 여전히 설계해야 한다.

## 1.2 흐름의 유형

### 클라우드 흐름

클라우드 흐름은 서비스의 이벤트, 사용자의 실행, 일정에 의해 시작된다.

- **자동화된 흐름**: 메일 수신, SharePoint 항목 생성 등 이벤트로 실행
- **즉시 흐름**: 버튼, Power Apps, Teams 등 사용자의 요청으로 실행
- **예약 흐름**: 매일 오전 9시, 매월 말일처럼 일정에 따라 실행

### 데스크톱 흐름

데스크톱 흐름은 웹 브라우저나 Windows 애플리케이션의 사용자 조작을 자동화한다. API가 없거나 수정할 수 없는 레거시 프로그램에 유용하다. 다만 화면 구조, 해상도, 세션 상태에 영향을 받기 때문에 API 기반 흐름보다 더 많은 운영 관리가 필요하다.

### 비즈니스 프로세스 흐름

비즈니스 프로세스 흐름은 사용자가 정해진 업무 단계를 따라가도록 안내한다. 백그라운드에서 모든 일을 자동 처리하기보다는 영업 기회 관리, 심사, 상담처럼 사람이 단계별 정보를 입력하고 판단하는 업무에 적합하다.

## 1.3 API 자동화와 UI 자동화

자동화 방법은 다음 순서로 검토한다.

1. 표준 커넥터나 공식 API가 있는가?
2. HTTP API 또는 사용자 지정 커넥터로 연결할 수 있는가?
3. 파일 교환이나 데이터베이스 연계가 가능한가?
4. 다른 방법이 없을 때 데스크톱 UI 자동화를 적용할 것인가?

API는 화면 배치와 무관하고 구조화된 오류를 받을 수 있어 일반적으로 안정적이다. UI 자동화는 사람이 화면에서 할 수 있는 거의 모든 동작을 재현할 수 있지만, 팝업 하나나 버튼 위치 변경에도 실패할 수 있다. RPA는 만능 연결 장치가 아니라 마지막 연결 수단으로 보는 편이 안전하다.

## 1.4 자동화하지 말아야 할 업무

다음 조건에서는 자동화를 미루거나 범위를 줄인다.

- 업무 규칙이 매주 바뀐다.
- 입력 데이터가 대부분 비정형이고 판단 기준이 합의되지 않았다.
- 처리 빈도가 낮고 자동화 유지 비용이 더 크다.
- 예외율이 높고 예외 처리 담당자가 없다.
- 법적·재무적 책임이 큰 결정을 무인으로 처리하려 한다.
- 원본 시스템에 감사 기록이나 복구 수단이 없다.

> [!tip] 현장 원칙
> 나쁜 프로세스를 그대로 자동화하면 더 빠른 나쁜 프로세스가 된다. 먼저 불필요한 단계와 중복 입력을 제거한 뒤 자동화한다.

## 1장 체크리스트

- [ ] 자동화 대상의 시작과 종료가 명확한가?
- [ ] 클라우드 흐름과 데스크톱 흐름 중 선택 근거가 있는가?
- [ ] API 기반 연결을 먼저 검토했는가?
- [ ] 사람의 판단이 필요한 지점을 분리했는가?
- [ ] 자동화하지 않을 조건을 정의했는가?

# 2장. 자동화 후보를 선별하는 방법

## 2.1 좋은 자동화 후보의 특징

좋은 후보는 반복 빈도가 높고 규칙이 명확하며 입력이 표준화되어 있다. 여기에 오류 감소나 처리 시간 단축 효과가 크면 우선순위가 높아진다. 반대로 예외가 많고 규칙이 자주 바뀌는 업무는 구현보다 유지보수에 더 많은 시간이 들 수 있다.

## 2.2 자동화 우선순위 점수표

각 항목을 1점부터 5점까지 평가한다.

| 평가 항목 | 1점 | 5점 |
|---|---|---|
| 실행 빈도 | 월 1회 이하 | 하루 여러 번 |
| 건당 처리 시간 | 1분 미만 | 30분 이상 |
| 규칙 명확성 | 담당자마다 다름 | 문서화된 규칙 |
| 데이터 표준화 | 비정형 중심 | 구조화 데이터 |
| 오류 영향 | 영향이 작음 | 고객·재무 영향 큼 |
| 예외율 | 30% 이상 | 5% 미만 |
| 시스템 안정성 | 화면·규칙 자주 변경 | API·스키마 안정 |

단순 합계만 사용하지 않는다. 오류 영향이 크지만 자동화가 잘못되면 피해가 커지는 업무는 사람의 승인과 이중 검증을 포함해야 한다.

## 2.3 현재 프로세스를 기록하는 법

자동화 전 업무를 다음 형식으로 기록한다.

```text
시작 조건: 고객 문의 메일 수신
입력: 메일 본문, 첨부파일, 발신자
처리 단계: 분류 → 담당자 배정 → 접수번호 생성 → 회신
판단 규칙: 제품군, 긴급도, 계약 고객 여부
예외: 첨부파일 누락, 고객 식별 실패, 중복 문의
출력: SharePoint 접수 항목, Teams 알림, 고객 회신
종료 조건: 담당자와 접수번호 확정
```

이 기록에서 사람이 반복하는 단계와 사람이 판단해야 하는 단계를 구분한다. 전자는 자동화하고, 후자는 승인이나 예외 큐로 남긴다.

## 2.4 PoC 성공 기준

“흐름이 실행된다”는 성공 기준이 아니다. 다음처럼 측정 가능한 기준을 사용한다.

- 정상 입력 50건 중 49건 이상 자동 처리
- 중복 파일 100% 탐지
- 건당 평균 처리 시간 10분에서 2분 이하로 단축
- 실패 발생 후 5분 이내 담당자 알림
- 실패 건을 원본 데이터 손실 없이 재처리 가능
- 민감정보가 비승인 채널로 전송된 사례 0건

## 실습: 자동화 후보 평가

1. 최근 한 달간 반복한 업무를 10개 적는다.
2. 빈도, 시간, 규칙, 예외율을 점수화한다.
3. 상위 3개 업무의 현재 프로세스를 작성한다.
4. 각 업무에서 사람의 판단이 필요한 단계를 표시한다.
5. 가장 단순하고 효과가 측정 가능한 업무 하나를 PoC로 선택한다.

## 2장 완료 기준

- 자동화 대상과 제외 대상이 분리되어 있다.
- 현재 프로세스와 목표 프로세스가 문서화되어 있다.
- 성공·실패 기준이 숫자로 정의되어 있다.
- 예외 처리 담당자와 수동 처리 경로가 정해져 있다.

# 3장. 첫 번째 클라우드 흐름 만들기

## 3.1 실습 시나리오

특정 제목의 메일에 첨부된 파일을 SharePoint 문서 라이브러리에 저장하고 Teams로 처리 결과를 알린다.

```text
Outlook 메일 수신
  → 발신자·제목·첨부파일 검증
  → SharePoint에 파일 저장
  → 성공 시 Teams 알림
  → 실패 시 운영 담당자에게 오류 알림
```

## 3.2 준비 사항

- Power Automate에 접근 가능한 회사 또는 학교 계정
- 테스트용 Outlook 사서함
- 파일을 저장할 SharePoint 사이트와 문서 라이브러리
- 알림을 받을 Teams 채널 또는 사용자
- 운영 데이터와 분리된 테스트 폴더

## 3.3 흐름 만들기

1. Power Automate 포털에서 새 자동화된 클라우드 흐름을 만든다.
2. Outlook의 새 메일 수신 트리거를 선택한다.
3. 제목 필터와 첨부파일 포함 조건을 설정한다.
4. 첨부파일별 반복에서 파일 이름과 콘텐츠를 가져온다.
5. SharePoint의 파일 만들기 작업으로 테스트 폴더에 저장한다.
6. 저장 결과를 포함한 Teams 메시지를 전송한다.

화면의 필드 이름은 업데이트에 따라 달라질 수 있다. 중요한 것은 트리거가 반환하는 값과 각 작업이 요구하는 입력을 이해하는 것이다.

## 3.4 처음부터 넣어야 할 방어 장치

### 파일명 정리

운영체제나 SharePoint에서 허용하지 않는 문자를 제거하고, 파일명이 비어 있을 때 대체 이름을 만든다.

### 중복 방지

다음 중 하나를 선택한다.

- 동일 경로에 파일이 있으면 건너뛴다.
- 타임스탬프나 메일 ID를 파일명에 추가한다.
- 별도 처리 이력 목록에 메일 ID를 저장한다.

메일 ID를 처리 키로 사용하면 흐름이 재실행되어도 같은 메일을 다시 처리하지 않는 멱등성을 구현할 수 있다.

### 오류 처리

핵심 처리 작업을 Scope로 묶고 성공, 실패, 종료 Scope를 분리한다. 실패 Scope는 `Run after` 설정을 사용해 실패·시간 초과 시 실행되도록 한다.

```text
Scope - Try
  ├─ 입력 검증
  ├─ 파일 저장
  └─ 성공 기록

Scope - Catch
  ├─ 오류 정보 구성
  ├─ 실패 기록
  └─ 담당자 알림

Scope - Finally
  └─ 실행 종료 정보 기록
```

## 3.5 테스트 케이스

| 번호 | 입력 | 기대 결과 |
|---|---|---|
| T01 | 정상 첨부파일 1개 | 파일 저장, 성공 알림 |
| T02 | 첨부파일 3개 | 3개 모두 저장 |
| T03 | 첨부파일 없음 | 저장하지 않고 사유 기록 |
| T04 | 동일 메일 재처리 | 중복 저장하지 않음 |
| T05 | 허용되지 않는 파일명 | 정리된 이름으로 저장 |
| T06 | SharePoint 권한 제거 | 실패 기록과 담당자 알림 |
| T07 | 대용량 파일 | 제한에 따른 명확한 실패 처리 |

## 3.6 실행 기록 읽기

흐름의 실행 기록에서 트리거 입력, 각 작업의 입력·출력, 실행 시간, 재시도 여부를 확인한다. 오류 메시지만 읽지 말고 어느 작업까지 성공했는지 확인해야 한다. 중간 단계가 이미 외부 시스템을 변경했다면 재실행 전에 중복 처리 가능성을 검토한다.

## 3장 완료 기준

- 정상·예외 테스트가 모두 수행되었다.
- 실패 알림에 흐름 이름, 실행 ID, 실패 단계, 발생 시간이 포함된다.
- 같은 입력을 다시 실행해도 중복 결과가 발생하지 않는다.
- 연결 소유자와 운영 담당자가 문서화되어 있다.

# 부록 설계

## 부록 A. 명명 규칙

```text
[환경]-[업무영역]-[행위]-[트리거]
DEV-HR-입사자계정요청-Form
PRD-FIN-월마감알림-Schedule
```

작업 이름에는 동사와 대상을 포함한다. `Compose 2`, `Condition 5` 같은 기본 이름은 운영 로그에서 의미가 없으므로 `Compose - 표준 파일명`, `Condition - 승인 한도 초과 여부`처럼 바꾼다.
