# 2024-10-20 223626672585 UML - 사물(Thing)과 관계(Relationship)를 표현

​

UML(통합 모델링 언어)에서 사물(Thing)과 관계(Relationship)는 시스템의 구조와 동작을 명확하게 표현하는 데 중요한 요소이다. 

​

​

**1\. 사물(Thing)**

사물은 UML에서 주체를 나타내며, 클래스(Class), 객체(Object), 컴포넌트(Component), 노드(Node) 등 여러 형태로 표현될 수 있다. 

  * **클래스(Class)** : 공통된 속성과 행동을 가진 객체의 집합을 정의한다. 클래스는 사각형으로 표시하며, 클래스 이름은 상단에 위치한다.

  * **객체(Object)** : 클래스의 인스턴스로, 구체적인 값을 가진 사물이다. 객체는 클래스와 비슷하게 사각형으로 표현되지만, 객체 이름과 함께 클래스 이름이 콜론(:)으로 구분되어 표기된다.

​

= Structural Things + Behavioral Things + Grouping Things + Annotation Things

**① Structural Things**

* Class : 같은 종류의 객체 집합

​

* 인터페이스 : 오퍼레이션을 선언만 하고 구현하지 못함.

* Collaboration(협력) : 구현관점에서 어떤 목적을 달성하기 위한 일련의 행위

* Use Case : 시스템이 제공하는 서비스 혹은 기능단위 

* Active Class : 하나 이상의 프로세스나 스레드를 갖는 객체를 파생하는 클래스 기술 

* Component : 시스템에서 독립적인 실행단위 혹은 배포단위로 관리되는 한 묶음의 SW 

​

* Node : 연산능력이 있는 물리적 요소(컴퓨팅) 

**② Behavioral Things(행위사물)**

* Interaction(교류) : 객체들간 주고받는 메시지 

​

* State Machine(상태머신) : 객체의 상태와 상태 간 허용된 액션 정의 

![](https://blog.kakaocdn.net/dn/dPVP73/btr36FEJimP/uW3JuqLsJxfzvWovKPpt8k/img.gif)

**③ Grouping Things(그룹사물)**

* Package : UML요소를 그룹으로 묶어놓은 것

**④ Annotation Things(주해사물)**

* Note : 주석 

​

​

**2\. Relationship(관계)**

UML에서 관계는 사물 간의 상호작용을 나타낸다.

​

**① Dependency**

한 클래스가 다른 클래스를 사용하는 관계를 나타내며, 점선 화살표로 표시된다. 

의존 관계는 일반적으로 일시적이거나 변경 가능성이 있는 관계를 표현할 때 사용된다.

​

한 쪽사물이 그 역할을 수행키 위해 다른 사물의 도움이 반드시 필요한 경우 

**표기법** : 점선 화살표로 표시되며, 화살표의 방향은 의존하는 클래스에서 의존받는 클래스로 향한다.

​

​

**② Association**

두 클래스 간의 관계를 나타내며, 일반적으로 실선으로 표시된다. 

연관의 방향성을 나타내기 위해 화살표를 사용할 수 있으며, 다중성(Multiplicity)을 통해 관계의 수를 표현할 수 있다.

​

한 쪽 사물에서 상대편 사물 참조.

​

**표기법** : 실선으로 표시되며, 다중성(Multiplicity)을 나타내기 위해 숫자나 기호를 추가할 수 있다.

​

​

**③ Generalization**

클래스 간의 상속 관계를 나타내며, 일반적으로 빈 삼각형 화살표를 사용하여 상위 클래스에서 하위 클래스로 향하도록 표시된다.

​

상속관계

​

**④ Realization**

인터페이스와 그 인터페이스를 구현하는 클래스 간의 관계를 나타낸다. 이는 클래스가 특정 인터페이스의 계약을 구현한다는 것을 의미한다.

**​**

선언하는 사물과 구현하는 사물 간 관계.

**표기법****: 점선 삼각형 화살표로 표시되며, 삼각형의 끝 부분이 인터페이스 쪽으로 향한다.**

​

> **Diagram = Things + Relationships**

**3\. Diagram**

**① Usecase Diagram**

* 용도 - 사용자관점에서 논리적인 시스템의 기능 정의

\- 인수측과 개발측이 이해를 같이하는 도구

\- 시스템 전체 개발범위 결정

\- 시스템 분석, 설계 기준

\- 인수테스트 기준

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**② Class Diagram**

* 용도 - SW의 기본구성단위인 클래스와 그들간의 관계 정의

\- 정적인 관점에서 클래스 구조 표현

\- 기본적 데이터 모델링 수행(분석단계)

\- 객체지향 언어코딩을 위한 설계 사양 제공(설계단계)

\- 분석에서 설계까지 일관된 형식의 SW시스템 분석, 설계 도구

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**③ Sequence Diagram**

* 용도 - 객체들간 협력 과정을 동적으로 정의한 Diagram

\- 유즈케이스 단위로 작성

\- 분석에서 설계까지 일관된 형식의 SW 시스템 분석 설계 도구

\- 클래스 다이어그램과 병행되며 상호간 일관성 요구됨

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**④ Collaboration Diagram**

* 용도 - Sequence Diagram과 동일함.

\- 객체와 메시지를 구조적으로 표현.

\- Sequence Diagram과 의미 손실 없이 변환 가능.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**⑤ State Chart Diagram**

* 용도 - 하나의 객체가 생성되어 소멸 될 때까지의 모든 상태를 분석 표현.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**⑥ Activity Diagram**

* 용도 - 일(Activity)의 수행 순서와 처리흐름 모델링. 플로우 차트와 용도 비슷.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**⑦ Component Diagram**

* 용도 - 컴포넌트로 이루어진 구성체계 표현. 정적 구성관계 표현.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**⑧ Deployment Diagram**

* 용도 - 컴퓨팅 환경인 노드와 그 노드에 배치할 컴포넌트 구성을 나타냄.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현

**⑨ Object Diagram**

* 용도 - 특정 조건하에서 주요 객체들의 속성과 객체관계를 분석함으로써 클래스 모델의 완전성 검증.

* 작성시기

요구정의→분석→기본설계→상세설계→개발→구현
